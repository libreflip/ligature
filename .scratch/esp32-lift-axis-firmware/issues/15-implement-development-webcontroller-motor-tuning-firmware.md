# Implement development-only WebController motor-tuning firmware

Type: task
Status: resolved
Blocked by: 05, 06, 14

## Question

Implement and exercise the smallest firmware path that lets the stock SimpleFOC commissioning interface tune the geared motor assembly: Motor 1 with its 10:1 gearbox attached and the gearbox output otherwise unloaded. Does the resulting development firmware provide motionless GUI discovery and telemetry, then explicitly authorized bounded closed-loop velocity and position tuning, without exposing the unrestricted stock motor callback or weakening the powered smoke-test safeguards?

### Implementation scope

- Add a dedicated `motor-tuning` PlatformIO environment and firmware entry point. Do not change the validated Hall or motor-smoke environments.
- Keep Motor 0 PWM controls low. Boot, reset, opening WebSerial, reconnecting, and ordinary parameter reads must leave Motor 1 PWM off and must not run alignment.
- Register a project-owned Commander adapter under the motor identifier expected by WebController. Forward stock motor commands unchanged except for the explicit alignment/enable handling and global hardware bounds below.
- Support WebController and Studio discovery, stock monitoring, and the stock reads/writes used to tune Motor 1.
- Require an explicit supervised serial command for bounded alignment and an explicit interface action to enable GUI-originated motion. After successful alignment, the commissioning interface may stage a bounded target while disabled, then use its stock enable/disable control through the project adapter; enable must remain rejected before alignment. Disable clears the staged target so a later enable cannot resume stale motion. Alignment failure, reset, fault, immediate stop, and session exit must command Motor 1 PWM off and disarm. After a runtime fault with alignment still valid, an explicit interface disable may clear the fault to aligned/disarmed while preserving volatile tuning values; failed alignment or invalid hardware state requires `XALIGN` retry or reset. This reduced-scope development firmware intentionally has no arm deadline; use the commissioning interface's disable control before leaving the supervised session.
- Use the current geared-motor tuning defaults of 3.0 V, 1.5 A operating current, and 100 rad/s. Intercept only global voltage/current/velocity-limit writes above 24.0 V, the measured symmetric 2.9 A ADC current range, and the motor's rated 3000 rpm (314.159 rad/s); reject non-finite values for those limits. Position and torque targets pass through unchanged; velocity targets retain the rated-speed bound and require alignment. Allow all stock SimpleFOC motion and torque modes and all other stock parameter, monitoring, characterization, and autotune commands. Keep raw `MFR` reinitialization blocked in favor of bounded `XALIGN`; persistence and profile promotion remain unavailable. The 2.9 A value is based on the lower side of the operator-observed asymmetric ADC range. In voltage torque mode SimpleFOC does not update measured current through its current-control path, so the software gross-current cutoff is not reliable; use a deliberately low voltage limit for supervised voltage-mode diagnostics.
- Service control work before bounded serial/monitoring work and report measured loop timing. In this reduced-scope Studio path, use SimpleFOC's stock `motor.monitor()` behavior and select a conservative downsample during the supervised test rather than adding custom automatic telemetry shedding.
- Add host-testable coverage for command authorization, bounds, reset/stop behavior, and representative WebController command strings where practical.

### Acceptance procedure

1. Build the new environment and rerun existing host tests plus the three existing firmware builds.
2. With bridge power supervised and the geared motor assembly initially motionless, connect the stock commissioning interface from the actual macOS host. Confirm discovery, parameter reads, and low-rate plots while PWM remains off.
3. Confirm browser reconnect/DTR reset returns to motionless, disarmed operation and does not align.
4. Explicitly run bounded alignment and capture project PASS with PWM off, then arm through the commissioning interface. Demonstrate five seconds of continuous closed-loop motion at ±75 motor-side rad/s whose average observed velocity remains within ±20 percent of target, with no stall, unintended reversal, or fault. Characterize ±10 rad/s rather than silently accepting unstable motion; route any repeatable low-speed limit to a separate control-strategy decision. After commanding zero, observe no further Hall transitions for two seconds.
5. Demonstrate cascaded position control through one complete gearbox-output revolution in each direction (±20π motor-side radians from the starting position). Reach and hold each target for two seconds within one output-side Hall sector (approximately 1.5° output or 0.262 motor-side rad) without repeated direction reversals, visible hunting, or nuisance faulting. This is the intended acceptance criterion; if device evidence shows it is physically unattainable with the Hall feedback, record that result and route the resulting architecture decision rather than silently weakening the criterion.
6. Confirm the commissioning interface's disable control commands PWM off. Record the highest telemetry rate tried and the measured control-loop timing. Physical injection of an eligible runtime fault is explicitly skipped for this development acceptance; host coverage verifies the recovery state transition, but no device-level recovery claim is made.

Compilation and automated tests are separate from physical validation. The ticket resolves when the operator-run commissioning check and any explicitly-routed limitations are recorded. This ticket does not implement profile JSON/NVS, production calibration validity, the belt-driven lift axis, homing, touchdown, the production protocol, or production acceptance.
